## It Started With a Model Swap

OpenClaw is the local AI assistant gateway I run as a launchd service on macOS. Today I switched the primary agent to a third-party model and restarted the gateway so the new config would take effect. The gateway never came back healthy — messages went unanswered, and the logs filled up with `send failed: GatewayClientRequestError`.

Over the next two hours I hit six distinct bugs, each more hidden than the last.

## Bug 1: chat.send Sends an Extra sessionId

The first error was clear: `invalid chat.send params: at root: unexpected property 'sessionId'`.

Digging into the compiled TUI bundle, OpenClaw 2026.5.7 was injecting a `sessionId` field into the `chat.send` RPC call. The server-side API doesn't accept that parameter and rejected the request outright.

```javascript
// dist/tui-JpbpfkGx.js line 1779
await this.client.request("chat.send", {
  sessionKey: opts.sessionKey,
  ...opts.sessionId ? { sessionId: opts.sessionId } : {},  // ← shouldn't be here
  message: opts.message,
  // ...
});
```

Fix: delete that one line. But there's also a separate copy of the compiled bundle under `plugin-runtime-deps` — both had to be patched.

## Bug 2: ERR_MODULE_NOT_FOUND — Stale Module Cache

After the sessionId fix, a fresh window produced: `Cannot find module 'session-archive.runtime-Dn7_buop.js'`.

That hash didn't exist on disk — the actual file was `session-archive.runtime-BbaVoTST.js`. The cause: the gateway process had been running since May 1st with the old module paths cached in memory. Meanwhile, OpenClaw had been upgraded via brew to 2026.5.7, which changed all the dist file hashes. The old process was still looking for files that no longer existed.

`launchctl kickstart -k` should have fixed it. But that led to the next bug.

## Bug 3: Service Disappears from launchd After kickstart

After the kickstart, the gateway restarted. A few minutes later it received SIGTERM and exited — and `ai.openclaw.gateway` vanished from `launchctl list` entirely. Not a crash; the service was unregistered.

The culprit: during debugging I had manually started a `node ... gateway --port 18789` in the background, which conflicted with the launchd-managed instance over the same port. The two processes fought, and one got killed.

Killed the manual process, re-registered via `launchctl bootout` + `bootstrap`.

## Bug 4: Plist Rewritten as an Empty File

With the service restored, the gateway started receiving SIGTERM every ~5 minutes and dying. Despite KeepAlive=true, launchd never restarted it.

The key clue: the plist file was modified at the exact second the SIGTERM arrived — and it had been truncated to 0 bytes.

Root cause: the old plist was hand-written with all environment variables (proxy, token) hardcoded directly in the XML. The new OpenClaw version switched to managing env vars through a `service-env/` wrapper. When the `gateway restart` command detected the incompatible format, it tried to rewrite the plist — but the format mismatch was so severe that it wrote out an empty file instead.

Fix: `openclaw gateway install --force` to let OpenClaw generate a proper standard-format plist.

## Bug 5: install --force Drops Proxy Settings

This fixed the plist problem and the gateway started successfully. But it still crashed every 5 minutes.

Looking at the env file generated by `install --force`, all proxy settings were gone. HTTP_PROXY, HTTPS_PROXY, all_proxy — none of them survived the migration from the old hardcoded plist to the new env-file format.

The third-party model API I'd configured requires a proxy to reach from China. No proxy → model API unreachable → calls fail → health monitor detects anomalies → `commands.restart = true` in the config triggers an automatic restart → restart still has no proxy → crash again. A perfect infinite loop.

Adding the proxy lines back to `~/.openclaw/service-env/ai.openclaw.gateway.env` finally stabilized the gateway.

## The Causal Chain

These six bugs weren't independent — they formed a single causal chain:

```
Swap model → trigger gateway restart
  → restart detects incompatible plist → writes empty file (Bug 4)
  → fix with install --force → proxy settings dropped (Bug 5)
  → model unreachable → health-check restart loop (Bug 5 consequence)
  → manual debug process conflicts with launchd (Bug 3)
  → old process still has sessionId bug (Bug 1) and stale module cache (Bug 2)
```

## The Safe Upgrade Procedure

Based on this experience, here's the procedure I'll follow for future OpenClaw upgrades:

```bash
# 1. Upgrade
brew upgrade openclaw

# 2. Stop the old gateway
launchctl bootout gui/$(id -u)/ai.openclaw.gateway

# 3. Regenerate the plist (critical!)
openclaw gateway install --force

# 4. Check the env file, restore proxy settings
vim ~/.openclaw/service-env/ai.openclaw.gateway.env
# Make sure HTTP_PROXY / HTTPS_PROXY / all_proxy are present

# 5. Start
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/ai.openclaw.gateway.plist

# 6. Verify (wait 5+ minutes to confirm no restart loop)
openclaw health && sleep 300 && ps aux | grep openclaw
```

The manual proxy restoration between steps 3 and 4 is the easiest step to forget. `install --force` doesn't migrate your old proxy settings — it doesn't even know they existed.

I've packaged this debugging experience into an `/openclaw-troubleshoot` skill with a decision table, so next time something breaks I can follow the flowchart instead of rediscovering each bug from scratch.
